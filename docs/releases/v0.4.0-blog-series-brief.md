# Post 4 — The Release Post

## Suggested Titles

- Looking at a Unity Dependency Graph Instead of Querying It
- A 2D, DAG, and 3D Asset Graph Viewer for Unity
- UAsset Reference MCP v0.4.0: Seeing the Graph

## Audience And Thesis

**Audience:** Unity developers and technical artists who have an asset
dependency problem but do not know which question to ask yet.

**Thesis:** A query answers a question you already have. A large dependency
graph's real problem is that you do not know which question to ask, so the tool
now shows you where to look before you ask anything.

## Problem Summary

The first three releases made the graph queryable: dependencies, references,
unused assets, traces. Every one of those requires knowing what to name. On a
project with 32,000 assets, the hard part is not answering "what references this
material" — it is knowing that this material is the one worth asking about.

## Solution Narrative

1. The viewer renders the graph directly, in three modes: 2D, DAG for
   hierarchy, and 3D for structure.
2. An attention panel answers the question the user has not asked yet: what is
   broken, what is orphaned, what is depended on most heavily.
3. Filters by asset type and origin, plus a node budget, keep a large project
   navigable rather than a hairball.
4. It starts with no arguments: run it inside a Unity project and it locates the
   project the way `git` locates a repository, then picks its own free port.

## Trade-Offs And Boundaries

- The viewer needs the local server, because it reads through the same HTTP API
  the MCP tools use. The server-less WASM flavor still exists as a separate
  download; it is no longer inside the npm package.
- The previous Cytoscape viewer is still shipped, at `/legacy.html`.
- 2D, DAG, and 3D are rendering modes, not more information. All three show the
  same graph; only 3D loads three.js, and it does so on demand.
- The node budget bounds what is drawn, not what is indexed.

## Suggested Article Outline

1. Three releases of query tools, and the question they cannot answer.
2. What a 32,000-asset graph looks like, and why a list is the wrong shape.
3. The attention panel: broken, unused, most-referenced.
4. Three ways to draw the same graph: 2D, DAG, 3D.
5. Filters, origins, and the node budget.
6. Starting it: no path, no port, no config.
7. What is not in it, and where the server-less flavor went.

## Factual Checklist

- The viewer is served at `/`; the previous viewer is at `/legacy.html`.
- It requires the local server; the WASM flavor is a release-page download.
- Port selection starts at 7777 and advances to the first free port.
- Project discovery walks up for `.asset-memory`, or `Assets` plus
  `ProjectSettings`.
- Five API routes were added: `asset-detail`, `broken-references`, `graph`,
  `index-status`, `root-trace`.
- The MCP tool count is unchanged at 15.
- Do not claim the viewer edits, refactors, or deletes anything. It is read-only.

# Post 5 — The Measurement Post

## Suggested Titles

- We Almost Rewrote Our Unity Indexer in Rust
- The Bottleneck Was Never the Language
- Measuring Before Rewriting: A Unity Asset Indexer in Node and Rust

## Audience And Thesis

**Audience:** tooling engineers, and anyone who has been told their bottleneck
is the language.

**Thesis:** A Rust port of the hot parser was 2.9x faster at parsing and made
the tool slower. Measuring the real project, on real data, moved the bottleneck
somewhere neither implementation touched — and the honest version of this story
includes being wrong twice on the way there.

## Problem Summary

Reference extraction parses Unity YAML looking for `{fileID, guid}` pairs. It is
the most obviously compute-heavy step in indexing and therefore the obvious
candidate for a native rewrite. A Rust proof of concept was built, produced
byte-identical output, and was benchmarked properly.

## The Numbers That Mattered

Same 2,000 records, exact output parity:

| Mode | End-to-end | Inner extraction |
| --- | ---: | ---: |
| Node, 8 workers | 3.146 ms | 3.146 ms |
| Rust, 8 threads | 119.852 ms | 1.074 ms |

Rust parsed ~2.9x faster and delivered ~38x slower, because spawning a process
and serializing NDJSON cost ~118 ms that the in-process path never pays.

An in-process binding would erase that overhead — which turns the question into:
how much of indexing is parsing at all?

## The Two Wrong Answers

This is the part worth writing honestly.

- The repository's own fixture generated 100-byte assets with one reference
  each. It measures per-file overhead, not parsing, and suggested parsing was
  ~3% of runtime.
- A replacement fixture generated 139 references per asset and suggested SQLite
  writes were ~76% of runtime.
- The real project has **0.89 references per asset**. The second fixture was
  ~150x too dense — wrong in the opposite direction from the first.

Both synthetic corpora encoded an assumption about shape, and both assumptions
were wrong. Only the real project settled it.

## What The Real Project Showed

A real 32,579-asset Unity project, at concurrency 8:

| Phase | Share |
| --- | ---: |
| scan | ~60% |
| extract (read + parse) | ~33% |
| write | ~6% |

Parsing alone is ~485 ms serial out of ~5,000 ms — roughly 2% once parallelized.
Then scan decomposed further: ~160 ms of directory traversal and ~400 ms of
`.meta` reads, against a phase reporting 1,600-3,000 ms. **Around 65-80% of the
dominant phase was not filesystem work at all** — it was promise-scheduling
overhead from concurrency pools nested per directory.

The bottleneck was coordination, in a language whose scheduler you do not
rewrite by switching languages.

## Trade-Offs And Boundaries

- The decision is recorded as an ADR with two explicit conditions for revisiting:
  a real-project breakdown showing parsing actually dominates, and an in-process
  binding rather than a subprocess.
- The Rust crate was kept, not deleted; the measurements are only reproducible
  because it exists.
- The Node parser is not fast in absolute terms — ~151-266 MB/s. It is simply
  not the bottleneck.
- Measurements come from one machine. The concurrency figures carry 8-9%
  variance, close to their own effect size, and the post should say so.

## Suggested Article Outline

1. The obvious optimization, and why it was obvious.
2. Building the Rust extractor; byte-identical output.
3. 2.9x faster, 38x slower: what a subprocess costs.
4. The fixture that said 3%, and the fixture that said 76%.
5. 0.89 references per asset: what the real project actually looks like.
6. Scan is 60%, and most of scan is not I/O.
7. What actually got faster: bounded concurrency, and a cap set from core count
   on a workload that is 93% waiting.
8. The conditions under which Rust would win, written down so the argument does
   not have to happen twice.

## Factual Checklist

- Rust parsed ~2.9x faster in-process and ~38x slower end-to-end via subprocess.
- The subprocess overhead was ~118 ms, from process start plus NDJSON.
- The real project: 32,579 assets, 28,842 edges, 0.89 edges per asset.
- Phase shares at concurrency 8: scan ~60%, extract ~33%, write ~6%.
- Parsing is ~485 ms serial; ~2% of total once parallelized.
- Raw scan I/O is ~560 ms against a 1,600-3,000 ms phase.
- Parallel indexing measured 2.7x on the fixture; concurrency 32 measured ~1.25x
  further on the real project, with identical output.
- Do not claim Rust is slow. Claim the subprocess was the wrong shape and the
  parser was the wrong target.
- Do not present the two wrong fixtures as a rhetorical device. They were real
  mistakes and the post is better for saying so.

# Post 6 — The Distribution Post

## Suggested Titles

- Ship the Tool, Not the Toolchain
- 93 MB Nobody Ever Executed
- Packaging a Unity Tool for Two Package Managers at Once

## Audience And Thesis

**Audience:** anyone publishing a developer tool, particularly one that spans a
JavaScript runtime and a game engine.

**Thesis:** A dependency is not a runtime dependency because your code imports
it. It is a runtime dependency when the installed artifact needs it — and for a
tool with a bundled UI, most of the UI's dependencies fail that test.

## Problem Summary

The tool ships three binaries and a browser UI from one npm package, plus a
Unity Editor package that must not ship to npm at all. Three things were wrong:
a bundled viewer's build dependencies were declared as runtime dependencies, a
WASM viewer meant to be opened from disk was shipped inside a package that runs
a server, and fonts were shipped twice.

## Solution Narrative

1. Vite bundles the viewer at publish time, so `three`, `react` and the rest are
   build-time only. Verified by scanning every non-relative import in
   the built output: the server needs exactly three packages.
2. The server-less WASM viewer became a release-page download. It exists to be
   opened from the filesystem; it never needed to be inside an install that runs
   a server.
3. Fonts were shipping in both `.woff` and `.woff2`, across six subsets. Trimmed
   to latin and latin-ext WOFF2.
4. The Unity package is excluded by the `files` allowlist and installs through
   Package Manager instead, in four different ways.
5. Ports are selected rather than configured, so multiple projects need no
   coordination.

## The Numbers

- Production install: ~134 MB to ~40 MB.
- Published package: 1.45 MB to ~0.72 MB, 2.9 MB to 2.1 MB unpacked.
- Fonts: 704 KB across 54 files to 180 KB across 10.
- `npm audit` on a production install: 0 vulnerabilities, because the removed
  packages carried the advisories.

## Trade-Offs And Boundaries

- A `.unitypackage` is not a UPM package: it imports into `Assets/` and is not
  upgradable in place. Say so plainly rather than listing it as an equal option.
- All three Unity formats are built without a Unity Editor, because the `.meta`
  GUIDs are committed. That is worth explaining — it is the reason no licence is
  needed in CI.
- Removing the WASM viewer from the package is a real removal for anyone using
  it, and the post should link where it went.
- Trimming font subsets means non-latin asset names fall back to a system font.

## The Bug Worth Including

Importing per-subset font CSS instead of the weight-level file looked correct,
produced exactly the right file count, and would have broken every glyph in the
UI: those files omit `unicode-range`, so two `@font-face` rules with the same
family and weight do not merge, and `latin-ext` — which contains only accented
characters — would have shadowed `latin`. The build was green. The file count
was right. Only reading the emitted CSS caught it.

## Suggested Article Outline

1. One package, three binaries, and a browser UI.
2. What "runtime dependency" means for a bundled frontend.
3. Finding the real answer: scanning imports in the built output.
4. The artifact that did not belong in the artifact.
5. Fonts, twice, in six alphabets.
6. The `unicode-range` bug that a green build hid.
7. Two package managers: npm for the tool, UPM for the Editor package.
8. Building `.unitypackage` without Unity.
9. Ports that pick themselves.

## Factual Checklist

- The built server imports exactly three packages: `zod`, `better-sqlite3`,
  `@modelcontextprotocol/sdk`.
- `files` in `package.json` is an allowlist; `unity/` and `rust/` are excluded by
  omission.
- A `.unitypackage` is a gzipped tar of `<guid>/{asset,asset.meta,pathname}`.
- `.tgz` requires a `package/` root; `.zip` is installed via Add package from
  disk; both are UPM-managed, `.unitypackage` is not.
- The Unity package versions independently and is at 0.2.0.
- Do not claim the tool got faster in this post. It got smaller.
