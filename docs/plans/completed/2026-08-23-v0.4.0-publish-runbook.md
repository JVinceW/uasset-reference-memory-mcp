## Approach

Two workflows do the work, and neither is triggered by the other:

- `.github/workflows/release.yml` — on push to `release/**`. Runs typecheck,
  tests, and build, then publishes to npm **only if the version is not already
  there**, choosing the dist-tag from the version: a hyphen means `next`,
  otherwise `latest`. Requires the `NPM_TOKEN` repository secret (an npm
  Automation token with publish rights and 2FA bypass).
- `.github/workflows/release-artifacts.yml` — on push of a `v*` tag. Builds the
  Unity package in three formats and the server-less viewer zip, then creates
  the GitHub release with notes taken from the matching `CHANGELOG.md` section,
  marking hyphenated versions as prereleases. Uses the built-in `GITHUB_TOKEN`;
  no secret needed.

Publish first, verify the registry, then tag. A tag therefore always means the
npm release is real — which is why the artifact workflow can trust it.

### Step 1 — publish to npm

```bash
git push origin HEAD:refs/heads/release/0.4.0
```

Wait for the Release workflow, then confirm the registry before tagging:

```bash
npm view unity-asset-reference-mcp dist-tags
# expect: latest 0.4.0
```

If `latest` still reads `0.3.2`, the publish did not happen — read the workflow
log rather than pushing again.

### Step 2 — tag, which builds the release page

```bash
git tag -a v0.4.0 -m "v0.4.0"
git push origin v0.4.0
```

Confirm the release page is **not** marked pre-release and carries four assets:
three Unity package formats and the static-viewer zip.

### Step 3 — after the release

```bash
npm install -g unity-asset-reference-mcp
unity-asset-reference-mcp-index index /path/to/UnityProject
cd /path/to/UnityProject && unity-asset-reference-mcp-web   # expect the new viewer at /
```

Then merge the release into `main`. No dist-tag housekeeping is needed: `next`
has never been used, so nothing points at a stale prerelease.

## Risks And Recovery

- **npm versions and Git tags are immutable.** Never reuse, replace, or
  force-push either. A mistake is corrected by publishing a new version, never
  by rewriting one.
- **If a prerelease lands on `latest`**, repoint it immediately —
  `npm dist-tag add unity-asset-reference-mcp@0.3.2 latest` — then fix the
  dist-tag logic before retrying. This is the failure the version-derived tag
  exists to prevent, and it is why step 1 verifies before tagging.
- **If the artifact workflow fails after npm published**, nothing is broken for
  users: npm is the install path and is already correct. Re-run the workflow via
  `workflow_dispatch` with the tag, or attach the assets by hand after running
  `npm run build:unity-artifacts` and `npm run build:static-viewer`.
- **If the release workflow reports "already on npm"**, the version was
  published previously; bump and retry rather than forcing.
- **`NPM_TOKEN` missing or expired** fails the publish step with a 401 before
  anything is written. Rotate the secret and push again; no cleanup needed.
- **The GitHub release page is created only by a tag.** `v0.3.1` and `v0.3.2`
  were tagged before this workflow existed and have no page; that is expected
  and needs no repair.

## Decisions

1. Only `0.4.0` ships. A candidate was prepared and then dropped: the only
   commit carrying the `0.4.0-rc.1` version string, `138be80`, predates seven
   commits of fixes, so publishing it would have put a knowingly stale build on
   npm — a release page still claiming the 2D renderer is Sigma, and an MCP
   server reporting version 0.1.0. npm versions are immutable, so that could not
   have been corrected afterwards. Rebuilding a candidate from current content
   was the alternative; releasing one version was chosen instead.
2. The prerelease pipeline is therefore unexercised. ADR 0019 and the
   version-derived dist-tag logic remain in place and tested by unit-level
   checks, but no prerelease has gone through them end to end.
3. The plan set was reconciled against the code rather than left as-is. The
   parallelism benchmark is completed, the never-started blog content handoff is
   closed as superseded, and the viewer plan had 22 items ticked on evidence
   with a note naming what is still genuinely unbuilt — chiefly browser
   validation, this release's largest untested surface.
4. The `.unitypackage` is shipped despite not being UPM-managed, because some
   teams require assets in the project tree. README says plainly that it does
   not upgrade in place.

## Validation

Performed on the release commit, on macOS with Node 24:

- `npm run typecheck`, `npm test` (45 files, 346 tests), and `npm run build` all
  pass.
- `npm pack --dry-run`: 147 files, ~726 kB packed, containing no `src/`,
  `docs/`, `rust/`, `unity/`, or `sql-wasm`.
- A production install (`npm install --omit=dev` from the packed tarball) runs
  all three binaries; the web server returns 200 for `/`, `/legacy.html`, and
  `/api/*`.
- Both artifact builders run and are covered by `scripts/build-artifacts.test.ts`.
- Changelog extraction verified for both tags against the file as it stands at
  each tagged commit, not just at HEAD.
- Upgrade path verified against a real 32,535-asset index built by an earlier
  version: served unchanged under 0.4.0, and a database forced to schema 2 was
  rebuilt automatically by a plain `index` run.
- The MCP server reports `0.4.0` over stdio, replacing a hardcoded `0.1.0`.

Not verified: browser rendering and interaction of the 2D/3D viewer, Windows
execution of `install.ps1`, and npm provenance, which only a real Actions run
produces.
